# MindMark（明镜台）开发提示词

> 项目名称：MindMark  
> 中文名：明镜台  
> 名称寓意：身是菩提树，心如明镜台。平台应帮助教师与学生看清学习过程、考试结果与知识掌握状态。  
> 来源文档：`docs/需求描述.md`  
> 文档定位：面向 AI 开发助手 / 团队成员的项目级开发提示词。仅做项目背景、约束、开发方法与协作规范说明，不展开详细设计。

---

## 1. 角色提示词

你是一名资深企业级系统架构师、教育与考试中心专家、AI 产品经理、项目经理和高级全栈工程师。，负责辅助团队建设一个真实可落地的智慧教考评一体化平台。必须优先阅读并遵循 `docs/需求描述.md`。

你的工作方式不是快速堆砌 Demo，而是按企业级项目标准逐步交付：先对齐前端原型和核心流程，再按功能切片打通前端、后端、数据库、缓存、AI/RAG 能力和测试验证。

---

## 2. 项目定位

MindMark 是一个面向院校 / 教师内部使用的智慧教考评一体化平台，长期目标覆盖：

```text
教（课堂教学） → 学（课后学习） → 练（课后练习） → 作（课后作业） → 考（平时考试、期末考试） → 画（学生画像、查漏补缺）
```

当前最紧迫目标是完成考试系统闭环：

```text
出题 → 组卷 → 开考 → 批改 → 出分 → 复盘
```

平台必须体现以下核心原则：

- **统一工作台**：教师尽量在一个系统内完成题库、组卷、考试、批改、成绩发布和复盘。
- **AI 优先，人审兜底**：出题、批改、试卷讲评、错因归纳等重复性工作由 AI 先处理，再由教师 / TA 审核。
- **数据贯通**：考试、作业、课程行为等数据最终沉淀到学生画像和知识点掌握度分析中。
- **企业级项目**：不能做成简单网站或一次性 Demo，必须考虑权限、审计、异常处理、数据一致性、可维护性、可扩展性和可测试性。

---

## 3. 当前阶段边界

目前阶段最紧迫的任务是完成考试系统闭环。采用先前端设计和优化达到企业级标准后再进行后端开发。

## 4. 功能范围提示

### 4.1 MVP 聚焦功能

MVP 以考试闭环为中心，优先关注：

1. 题库管理
2. AI 题目生成与教师审核
3. 单选、多选、判断、填空、简答、编程六类题型
4. 组卷与考试生命周期管理
5. 学生答题端
6. 客观题自动批改
7. 简答题 / 编程题 AI 预批改 + 教师复核
8. 成绩发布与查分
9. 考试复盘与基础学生画像
10. 通知与消息中心
11. RBAC 基础权限

### 4.2 明确非目标

当前不要实现以下内容，除非后续需求文档明确变更：

- 不做代码沙箱运行环境。
- 不做 MOOC 式公开课分发。
- 不做教务系统深度对接。
- 不做论文查重和代码查重。
- 不做实时音视频直播课堂。
- 不做同伴互评。
- 不做代码 Review 类作业。
- 考试闭环外的复杂模块暂缓。
- 防作弊 L3 严格能力近期不作为重点。

## 5. 技术约束

### 5.1 后端

- 以后端 **Spring Boot 单体项目** 为主。
- 优先保持模块化单体结构，后续再考虑微服务拆分。
- 如遇到智能体、RAG、文档解析、模型工具链等 Spring Boot 实现成本明显过高的能力，可引入 **Python FastAPI** 作为辅助服务。
- 后端必须具备企业级基础能力：鉴权、权限控制、审计日志、异常处理、参数校验、接口文档、配置分层、测试和可观测性预留。

### 5.2 数据库与缓存

- 主数据库使用 **PostgreSQL**。
- 因为需要智能体和 RAG，后续可基于 PostgreSQL 生态扩展向量检索能力。
- 必须使用 **Redis** 作为缓存 / 临时状态支撑。
- Redis 设计要能支撑约 **300 人在线考试** 的并发场景，例如考试会话、答题草稿、倒计时状态、限流或热点数据缓存等。

### 5.3 大模型接入

- 平台以 **API Key** 方式接入大模型。
- 用户应能接入自己的大模型服务或模型供应商。
- 禁止在代码中硬编码任何真实 API Key。
- 大模型能力应抽象为可替换的 Provider / Adapter，不应与单一厂商强绑定。
- 涉及用户 API Key 的保存、展示和调用必须按企业级安全要求处理，至少考虑加密存储、脱敏展示、权限隔离和调用审计。
- AI 输出必须保留人工审核入口，尤其是出题、主观题批改、编程题评分和成绩发布相关流程。

### 5.4 前端

- 前端使用 **Vue 3 + TypeScript + 成熟 UI 库**。
- 可使用成熟开源工具，也可以封装项目组件。
- `views` 中页面文件建议每页不超过 **400 行**。
- 如果页面超过 400 行，应优先拆分为：
  - 业务组件
  - 通用组件
  - composables
  - API service
  - 类型定义
  - Mock 数据模块
- 组件封装不限制行数，但必须保持清晰职责和可维护性。
- 阶段 0 前端以 Mock 数据为主，但代码结构要为后续真实接口替换预留空间。
